# Контекст проекта

## 1. О проекте

Рабочее название: `my-resume`.

Это интерактивное портфолио Frontend-разработчика. Оно должно не просто перечислять навыки и опыт, как обычное резюме, а позволять посетителю увидеть навыки в действии: взаимодействовать с демоверсиями, играть в небольшие игры и изучать визуальные эксперименты.

Главная цель — создать интересное, качественное и запоминающееся портфолио, которое одновременно демонстрирует технические навыки разработчика и умение продумывать пользовательский опыт.

## 2. Текущее состояние

Проект уже создан. Не нужно создавать новый проект, повторно инициализировать Vite или заново устанавливать существующие зависимости.

Текущий стек:
- React 19
- TypeScript 5.9
- Vite 8
- ESLint 10

Доступные команды:
- `npm run dev` — локальный запуск;
- `npm run build` — проверка TypeScript и production-сборка;
- `npm run lint` — проверка ESLint;
- `npm run preview` — локальный просмотр production-сборки.

В проекте пока не следует считать выбранными или установленными дополнительные библиотеки, роутер, систему управления состоянием, UI-kit или CSS-фреймворк. Перед добавлением зависимостей необходимо обосновать их необходимость.

## 3. Предполагаемая структура продукта

Структура предварительная. Её можно уточнять в процессе проектирования, но новые разделы и крупные функции необходимо согласовывать до реализации.

### Главная

- Краткое представление разработчика.
- Позиционирование: Frontend Developer.
- Небольшое описание специализации и подхода к разработке.
- Навигация по основным разделам портфолио.
- Визуальные элементы, которые сразу показывают интерактивный характер сайта.

### Мои навыки

Раздел с интерактивными демонстрациями технических навыков.

Предварительные идеи:
- демонстрация работы состояния и взаимодействий в React;
- CSS-анимация с настройками параметров;
- пример работы с данными: загрузка, успешное состояние, ошибка;
- форма с валидацией и типизацией.

На старте достаточно выбрать до трёх действительно полезных демонстраций. Не нужно реализовывать все идеи одновременно.

### Мини-игры

Раздел с небольшой законченной игрой, в которую посетитель может сыграть прямо на сайте.

Возможные варианты:
- Catch the Dot — поймать движущуюся точку;
- Memory Cards — игра на запоминание карточек.

Конкретная игра пока не выбрана.

### Лаборатория

Раздел для визуальных и технических экспериментов:
- частицы и движение;
- генеративные фигуры;
- геометрия;
- анимации и визуальные эффекты.

Эксперимент должен быть интерактивным или наглядно демонстрировать техническую идею, а не служить исключительно декорацией.

### Проекты

Раздел для настоящих проектов разработчика.

Структуру раздела можно подготовить заранее, но нельзя придумывать несуществующие проекты, результаты, метрики или ссылки. Если готовых проектов пока нет, необходимо честно отразить это в интерфейсе или временно не показывать раздел посетителям.

### Контакты

Ссылки на реальные контакты разработчика. Использовать только те адреса и профили, которые предоставлены и подтверждены владельцем портфолио.

## 4. Визуальное направление

Финальный стиль ещё не выбран.

Предварительное направление — сочетание профессионального минимализма и выразительных интерактивных деталей. Портфолио должно выглядеть достаточно профессионально для потенциального работодателя, но при этом иметь индивидуальность.

До согласования дизайна не нужно самостоятельно фиксировать окончательную цветовую палитру, шрифты, оформление карточек или конкретную визуальную концепцию.

## 5. Технический подход

- Использовать существующий React + TypeScript + Vite.
- Предпочитать простые и понятные решения без лишних зависимостей.
- Для стилей на начальном этапе рассматривать обычный CSS или CSS Modules.
- Не добавлять серверную часть, базу данных и авторизацию без отдельной необходимости.
- Не усложнять архитектуру ради архитектуры.
- Поддерживать типизацию TypeScript и не обходить её через `any` без обоснованной причины.
- Следить за разделением ответственности компонентов и повторным использованием действительно общих элементов.
- Проверять доступность интерфейса, клавиатурную навигацию и поведение на мобильных устройствах.
- Учитывать настройку пользователя `prefers-reduced-motion` для анимаций.
- Не допускать неоправданно тяжёлых анимаций и ухудшения производительности.

## 6. Архитектура проекта

Использовать **Feature-Sliced Design (FSD)** в упрощённом виде, без избыточной вложенности и абстракций. Архитектура должна помогать поддерживать код, а не усложнять его.

Основные правила:
- Соблюдать разделение на слои FSD и направление зависимостей: верхние слои могут зависеть от нижних, но не наоборот.
- Не создавать слои, слайсы и сегменты, пока в них нет необходимости.
- Выносить в `shared` только действительно переиспользуемый код.
- Не превращать каждый компонент в отдельную фичу.
- По мере роста проекта расширять архитектуру постепенно.

Пример возможной структуры:

```text
src/
├── app/          # Инициализация приложения, глобальные стили
├── pages/        # Страницы сайта
├── widgets/      # Крупные блоки интерфейса
├── features/     # Пользовательские действия и сценарии
├── entities/     # Сущности, если понадобятся
└── shared/       # Общие компоненты и утилиты
    ├── ui/
    └── lib/
```

Структура предварительная: использовать только необходимые слои и папки. Не создавать пустые директории ради соблюдения формальной структуры FSD.

## 7. Роль владельца проекта и AI-агента

Владелец проекта отвечает за продуктовые решения: содержание, приоритеты, визуальное направление и согласование крупных изменений.

AI-агент помогает прорабатывать требования, предлагать решения, реализовывать код и проверять результат.

Агенту следует объяснять важные архитектурные и технические решения простым языком. Не нужно без необходимости перекладывать на владельца написание кода вручную.

При этом код должен оставаться понятным и поддерживаемым: владелец проекта должен иметь возможность разобраться в реализации, проверить её и продолжить развитие проекта.
